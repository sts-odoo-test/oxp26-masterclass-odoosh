Where Odoo.sh fits

Three ways to run Odoo

Same product, three different ways to run it — the difference is who manages what, and how much control you get in exchange.

  • Odoo Online

    Odoo's own SaaS, fully hosted and managed.

  • On-Premise

    Self-hosted — you own the infrastructure (Day 1).

  • Odoo.sh

    Odoo's PaaS: managed infrastructure + full code access, git-driven.

Option 1

Odoo Online

  • What you getAn instance, duplicate, backups.
  • CustomizationStudio, configuration, and importable apps (data file only) — no server/shell/database access.
  • UpgradesAutomatic.
  • Best fitStandard business needs, no custom development, minimal IT involvement.

Option 2

On-Premise (Day 1)

  • OwnershipYou own the full stack: os, nginx, postgres, workers, filestore, backups.
  • FreedomAny custom code, any infrastructure choice, any deployment pipeline you build yourself.
  • The cost of that freedomYou're responsible for everything Day 1 covered: deployment, security, tuning, monitoring, backup strategy, ...
  • Best fitSpecific infra/compliance requirements, existing ops team, full control needed.

Option 3 — today's subject

Odoo.sh

A PaaS built specifically for developers running custom code — but still a managed solution, not just "a VM with git on it".

  • Managed infraWorkers, nginx, postgres, backups — same concerns as On-Premise, but Odoo operates them for you.
  • Full code accessGit branches, automatic builds, automated tests, staging environments, one-click restore.

On-Premise's flexibility, Odoo Online's operational simplicity.

Odoo.sh, concretely

What "managed" means day to day

  • Security updatesOS/system-level package updates are applied automatically — nothing to patch yourself.
  • Standard Odoo codeCore + Enterprise updated automatically weekly — latest bugfixes/security fixes, no action needed.
  • PostgreSQLPre-configured for the platform, not user-tunable — no postgresql.conf access, no extensions (PostGIS, ltree…).

Platform overview & branches

Branches, builds, workers, hosting tiers, the major-version upgrade flow.

The big picture

Dev flow on Odoo.sh

  • FlowDev branch → staging → production.
  • BranchesHandle the stage, rebuilt on every push.
  • BuildThe unit of work. A build = container + database + code.
  • Git-drivenPush triggers a build, tests run automatically. Promotion between branch types is explicit, not automatic.

Branches

  • DevelopmentOne per feature/fix, disposable, fresh demo database on every rebuild.
  • StagingTracks a dev branch's code, runs against a neutralized copy of production data.
  • ProductionThe one branch actually serving real users — nothing reaches it without an explicit merge/promotion.

Builds

  • MachineA specific machine is set with everything you need to run the chosen odoo version.
  • CodeThe standard code depending odoo version and your custom code. Can be modified on dev and staging builds
  • FilesystemThe container of your specific build

Workers: two models

On-Premise / Odoo Online
  • --workers=N pre-forks N single-threaded processes.
  • 1 worker = 1 request at a time.
  • Plus separate dedicated cron and longpolling workers.
Odoo.sh
  • Each "worker" is a complete, independent odoo-bin process, running multi-threaded.
  • 1 worker = several requests at once, by itself.
  • Scaling = more independent processes, routed by the platform's own layer.

Same word, different architecture — keep this model in mind for the rest of the day.

Workers: what you can actually scale

  • ConfigurableOnly the production branch's worker count.
  • Staging / devAlways capped at a single worker, on any hosting tier.
  • More workers ≠ fasterOnly increases concurrent connections. If operations remain slow, the issue is likely code-related.
  • Crons and emails1 dedicated worker, also multithreaded.

Backups

  • Production backupsAutomatic daily (7 daily + 4 weekly + 3 monthly).
  • Replicated3 different machines in different data centers in Europe and Canada.
  • Staging backupsManual only, kept 3 days, max 5/day.
  • Development backupsNone.

Tooling

What's available inside every build, dev to production.

  • Webshell & editorAccess to the container in a shell or with an editor.
  • SSHssh access
  • MonitoringMonitor the state of your container and build (memory, cpu, storage, etc...) - only for production and staging
  • Log viewerAllow to check the logs install.log, update.log, odoo.log.
  • ProfilerAllow to create a flamegraph.
  • Audit logsTracking of users actions (project level).

Access rights

Mimics the three stages of branches.

  • AdminProduction and project settings, and staging and dev environments.
  • TesterAccess to both staging and dev environments.
  • DeveloperDev builds.

More infoodoo.com/documentation/master/administration/odoo_sh/getting_started/settings.html

Hosting types: shared vs. dedicated

  • Shared hostingMultiple customers on the same server, fully isolated from other customers.
  • Dedicated hostingYour environment runs alone, fully isolated from other customers.
  • Worker rangeShared: 1-8 workers self-service. Beyond 8 → dedicated hosting.

Not the weekly thing

Major version upgrades — the process

Changing version (e.g. 17.0 → 19.0) is not automatic.

  • Integration with the upgrade platform.
  • Upgrade of last daily backup on staging.
  • Iteration on staging for code specific issue.
  • Upgrade on production triggered on git push.

Staging & the path to production

Neutralized production data, the merge flow, and what Odoo.sh does and doesn't validate.

Staging = neutralized production data

  • What staging isSame code as the branch it tracks, a neutralized copy of production data.
  • Standard OdooEvery Odoo.sh staging/dev database is neutralized — the same mechanism used for upgrade testing and backup restores everywhere.
  • DeactivatesScheduled actions, outgoing emails, bank sync, payment providers, delivery methods, IAP tokens, website SEO visibility.
  • On screenA red banner marks a neutralized database, so it's never mistaken for production.

Staging databases are auto-deleted after ~1 month of inactivity — rebuild the branch for a fresh one.

How neutralization actually works

  • 1

    Any installed module can ship it

    A data/neutralize.sql file — base, mail, payment already do, for the items on the previous slide.

  • 2

    The platform runs them automatically

    Every installed module's data/neutralize.sql, whenever it neutralizes a database.

  • 3

    A custom secret isn't covered

    It's just data no core module knows to touch — that's exactly the gap Exercise 4 is about.

Upgrade on Odoo.sh

The module-specific part: why pre_migration.py vs. post_migration.py.

Not the weekly thing

Major version upgrades — the process

Changing version (e.g. 17.0 → 19.0) is not automatic.

  • 1

    Request a test upgrade

    Odoo.sh sends your latest production backup to the Upgrade Platform.

  • 2

    Staging enters "upgrade mode"

    Every push restores the upgraded backup and updates your custom modules.

  • 3

    Test, fix, repeat

    Fix your custom module code for the new version, as needed.

  • 4

    Explicitly request the production upgrade

    A separate, deliberate action — not a side effect of a green staging test.

  • 5

    Triggered by a commit to production

    Synchronizes the DB upgrade with your upgraded custom code.

Upgrade on Odoo.sh

Request test → staging upgrade mode → test → request production → downtime.

  • Field changeMigration script
  • speaker (Char) → presenter_id (Many2one)post_migration.py
  • duration (Integer, minutes) → duration (Float, hours)pre_migration.py
  • Why pre vs. postPre runs before the ORM touches the schema (raw SQL only, old columns/tables still exist). Post runs after (new fields exist via the ORM, but start empty).
